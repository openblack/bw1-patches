# Throw Control

> Machine-readable definition: [`patches/throw_control.toml`](../patches/throw_control.toml) — apply it with the [`bw1patch`](../tool) tool.
> Bytes are generated by [`scripts/throw_control_asm.py`](../scripts/throw_control_asm.py).

Throwing is hard to control: a throw takes the hand's speed at the exact frame the button
is released, so easing off the mouse a moment before letting go loses most of it, and on
large screens or with high-DPI mice almost every flick comes out at full strength. This
patch makes a throw keep the fastest swing of the last moment and lets the throw strength
be scaled, both set in a small ini file.

## How throwing works

While the player holds an object and drags to throw, `HandStateHolding::Update`
(`0x005B3C70`, slot 3 of the `HandStateHolding` vtable at `0x00900B40`) sets `InThrow`
(`HandStateHolding+0x104`) and moves the hand as a damped spring towards the point on the
landscape under the cursor, in fixed 10 ms steps:

```
vel += ((target - pos) * 260 - vel * 40) * 0.01     // 0x00BF0198, 0x00BF019C, 0x00900B60
if (|vel| > 124) vel *= 124 / |vel|                  // 0x00C371FC
pos += vel * 0.01
```

The spring velocity is `HandStateHolding+0x108`. At the end of each update it is copied
into the hand (`CHand+0x48C8`, angular velocity `CHand+0x48D4` zeroed), and that is the
velocity the held object leaves with when the button goes up
(`Object::ThrowObjectFromHand` reads it back from the player's `GInterfaceStatus`).

The spring is stiff and slightly over-damped (it settles in about 0.1 s), so:

- the throw is the speed of the release frame: slowing down just before releasing kills
  it, and there is nothing on screen that shows this;
- the target is the cursor's point on the ground, so the further the camera is zoomed
  out and the more the cursor moves per mouse count, the faster that point moves: on a
  large screen or with a high-DPI mouse nearly every flick reaches the 124 cap.

## Patch

The velocity copy at `0x005B46BC..0x005B46E9` becomes `call cave; jmp 0x005B46EA`. The
cave (vaddr `0x008A8CA0`, after the other patches' caves) writes to `CHand+0x48C8` the
fastest velocity of the last `Grace` milliseconds of game frames (frame time in ms at
`0x00C38134`), multiplied by `Strength` / 100:

- when the spring velocity is exactly zero (`InThrow` was just set) the held velocity is
  cleared and the settings are read again;
- a velocity at least as fast as the held one replaces it;
- otherwise the held one is kept until it is older than `Grace` ms, then the current
  velocity replaces it.

The settings are read from `BWThrow.ini` in the game folder at the start of every throw
(the reset above also clears the loaded flag), so the file can be edited while playing:

```ini
[Throw]
Strength=60
Grace=150
```

`GetPrivateProfileIntA` is not imported by the game, so the cave resolves it with
`GetModuleHandleA("kernel32.dll")` and `GetProcAddress` (both in the IAT). Without the
file the defaults are `Strength=100`, `Grace=0`: exactly the original behaviour.

The cave's 32 bytes of state live at `0x00FBFF00`, in the zero-filled tail of `.data`
past its VirtualSize (the last object, `__jump_buffer`, ends at `0x00FBFE00`; the page
is mapped up to `0x00FC0000`).

Only the copy into the hand changes: the hand's own movement on screen is untouched.
In multiplayer all players should use the same settings.
