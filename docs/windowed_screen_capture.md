# Windowed Screen Capture

> Machine-readable definition: [`patches/windowed_screen_capture.toml`](../patches/windowed_screen_capture.toml) — apply it with the [`bw1patch`](../tool) tool.
> Bytes are generated by [`scripts/windowed_screen_capture_asm.py`](../scripts/windowed_screen_capture_asm.py).

In windowed mode (see [`windowed_mode`](windowed_mode.md)) every save-game thumbnail in
the temple's Save Game room renders as solid pink, and the on-disk
`save_game_picture_*.raw` files in `Saved Games\Pictures` contain a perfectly valid DXT1
image of solid magenta (`0xF81F` in RGB565). The downstream pipeline — DXT compression,
atlas blit, file write, texture upload — all works; it is the **screen grab itself** that
reads magenta instead of the rendered frame.

## How the game captures save pictures

When a game is saved, `GGame` queues a grab request (`0x00828E90` copies it to the global
block at `0x00EA9F70` and raises the flag at `0x00EB99B4`) and the grab routine at
`0x00821750` runs — the main loop also calls it right after `GGame::ProcessGraphicsEngine`
(i.e. right after the frame has been rendered *and presented*):

1. `IDirectDrawSurface7::Lock` on the **front buffer** `[0x00E85080]` (`LHScreen+0x30`).
2. CPU-converts the locked pixels — 16-bit 555, 16-bit 565 or 32-bit, dispatched on the
   locked surface's pixel format — into a 256×256×24 RGB buffer (two 128-row halves over
   two frames, selected by request field `+0x200`).
3. The buffer becomes a 256×256 DXT1 DirectDraw surface, is written to
   `save_game_picture_temporary.raw`, and `0x007923D0` blits it into the per-slot
   hires/lores atlas files.

A second variant at `0x00821370` does the same with a 400×300 buffer for named snapshot
captures, and locks the same front buffer.

## Why it breaks in windowed mode

Locking the front buffer is correct in fullscreen: after a flip it holds exactly the
frame just presented. In windowed mode the "front buffer" is the desktop primary surface,
and on modern Windows that's an emulated surface whose lockable memory never receives the
game's rendering — it reads back as a constant magenta fill. (Even on period hardware
this path was questionable in windowed mode: the grab applies no window-client offset, so
it would have sampled the top-left of the desktop.)

The back buffer `[0x00E85084]` (`LHScreen+0x34`) does not have this problem: windowed
mode presents with a `Blt`, which leaves the back buffer intact, and the grab runs right
after present — so at that moment the back buffer holds exactly the just-presented frame.
In fullscreen the back buffer is stale after the flip, so the front buffer must keep
being used there.

## Patch

A 21-byte routine in the `.text` zero pad (vaddr `0x008A8B80`) picks the surface based on
the windowed flag `LHScreen+0x64` (`0x00E850B4`, set by `LHScreen::SetFullscreenMode` —
`0` fullscreen, `1` windowed):

```nasm
cmp  dword ptr [0xE850B4], 0
jne  windowed
mov  eax, [0xE85080]        ; fullscreen: front buffer (last flipped frame)
ret
windowed:
mov  eax, [0xE85084]        ; windowed: back buffer (Blt-present leaves it intact)
ret
```

Every `mov eax, [0xE85080]` in the two grab routines is `A1 80 50 E8 00` — exactly five
bytes, the same size as a `call` — so each one is replaced with `call 0x8A8B80` and no
other bytes move. Five sites are hooked:

| vaddr | file offset | routine | role |
|-------|-------------|---------|------|
| `0x008217A8` | `0x4217A8` | save-picture grab | surface for `Lock` |
| `0x008217C2` | `0x4217C2` | save-picture grab | surface for early-out `Unlock` |
| `0x00821B53` | `0x421B53` | save-picture grab | surface for `Unlock` |
| `0x008213AE` | `0x4213AE` | snapshot grab | surface for `Lock` |
| `0x00821712` | `0x421712` | snapshot grab | surface for `Unlock` |

The routine clobbers only `EAX` (like the instruction it replaces) and `EFLAGS`; at every
hook site the next flag-reading instruction is preceded by a flag-setting one, so the
clobber is safe. Fullscreen behaviour is unchanged.

## Picture file format, for reference

Each `save_game_picture_*.raw` is `[u32 data size][124-byte DDSURFACEDESC][surface bits]`
— as shipped, a 256×256 DXT1 surface (32,896 bytes). `hires_%i.raw` holds two thumbnails
side by side, `lores_%i.raw` holds eight in a 2×4 grid; the in-game texture loader
(`0x008379E0`) re-creates whatever the embedded `DDSURFACEDESC` describes but resamples
the result to a 256×256 16-bit texture, so 256×256 is the effective ceiling of the whole
pipeline without further patching.
