# Widescreen Loading Screen

## Symptoms

On widescreen displays (16:9, 16:10, 21:9 …) the tip-of-the-day loading screen breaks
in three ways:

* the tip image is stretched horizontally instead of staying 4:3;
* the tip text under the progress bar disappears entirely;
* the bottom of the screen shows a lone thin gray strip where the text band should be.

On 4:3 and 5:4 displays everything looks fine.

## Cause

The tip loading screen is drawn by an unnamed helper at `0x005F3DC0` (called with a
fade-in fraction from `RenderLoadingFrame(bool)` @ `0x005F4E40`, see bw1-decomp). Its
entire layout is computed in one block at `0x005F3E5C..0x005F3F18` as fixed fractions
of the screen **width** `w` and **height** `h`:

| value | meaning | axis |
|-------|---------|------|
| `0.18 * w` | tip image left | x |
| `0.05 * h` | tip image top | y |
| `0.64 * w` | tip image **width** | size |
| `0.64 * h` | tip image height | size |
| `0.60 * w` | tip text band **top** | **y!** |
| `0.125 * w` / `0.875 * w` | tip text wrap left/right | x |
| `0.95 * h` | band bottom / version line | y |

The layout was authored assuming `w = 4/3 * h`:

* The image rectangle is `0.64w x 0.64h` — only 4:3 when the screen itself is 4:3.
  On 16:9 it adopts the screen's aspect ratio and stretches.
* The text band's *vertical* position is a fraction of the *width*: `0.6w` equals
  `0.8h` on 4:3, but `1.07h` on 16:9 — the band and both `GatheringText::DrawText`
  calls land **below the bottom edge of the screen**. That's why the text vanishes;
  the thin strip still visible is the band's bottom edge drawn at `0.95h`.

(You can verify the numbers against a 1280x1024 screenshot: image at x 230..1050,
y 51..707, band at y 768..973 — exactly `0.18w..0.82w`, `0.05h..0.69h`, `0.6w..0.95h`.)

## Fix

Replace the 189-byte layout block with a `jmp` into a small code cave that computes
the same eight values from an effective 4:3 width

```
cw   = min(w, h * 4/3)
xoff = (w - cw) / 2
```

* size and **y** values use `cw` instead of `w` (`0.6cw = 0.8h` — same as on 4:3, so
  the text comes back and the image becomes `0.64cw x 0.64h`, a true 4:3 rectangle);
* **x** positions additionally get `+ xoff`, keeping everything centred.

On 4:3 and 5:4 displays `cw == w` and `xoff == 0`, so the layout is unchanged. The
full-screen blurred backdrop, the bottom darkening gradient and the gray text band
intentionally keep using the real screen size — they should fill the screen.

The cave (194 bytes) sits in the `.text` tail zero-pad at `0x008A8AB0`, directly after
the [`saves_in_documents`](saves_in_documents.md) routine; both patches can be applied
in any order. It reuses the game's own `.rdata` float constants (0.125 @ `0x8AB620`,
0.875 @ `0x8AB618`, 0.6 @ `0x8C7BDC`, 0.18 @ `0x8C49E8`, 0.64 @ `0x8CA28C`,
0.95 @ `0x8CF000`, 0.05 @ `0x8AC3F4`, 255.0 @ `0x8AB270`) and preserves the block's
exact register/FPU contract (`esi = w`, `edi = h`, `eax = fade * 255`, x87 empty).

Bytes are generated by [`scripts/widescreen_loading_asm.py`](../scripts/widescreen_loading_asm.py)
(keystone). The hook op's `expect` is the entire original 189-byte block, so the patch
refuses to apply to anything but a matching executable.

## Out of scope

The plain progress-bar flash screen (mode 2 of `RenderLoadingFrame`) draws its
"Loading…" caption at fixed 800x600-ish coordinates; it is mildly off-centre on
widescreen but never broken, so it is left untouched.
