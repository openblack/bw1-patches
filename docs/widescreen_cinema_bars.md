# Widescreen Cinematic Bars

## Symptoms

In certain scenes (god conversations, scripted cutscenes) the game letterboxes the
view with animated black "cinema" bars. On widescreen displays (16:9, 16:10, 21:9 …)
the bars never appear, and cutscenes lose their cinematic framing.

On 4:3 and 5:4 displays they work as designed.

## Cause

The bars are driven by the `SET_WIDESCREEN` script command, which lands in
`HelpSystem::SetWideScreen` (`0x005C6AD0`, names from bw1-decomp). The state lives in
the `HelpSystem` object (`this+0x45E8` on/off flag, `this+0x45F0` transition timer),
and an updater (`0x005C6BB0`) publishes the animated 0→1 transition fraction to a
global at `0xEB9950` each frame.

The bar *height*, however, is computed everywhere from one formula:

```
bar_total = h − w * 0.5625          ; 0.5625 = 9/16, .rdata @ 0x8C7A50
                                    ; w/h = interface size ints @ 0xE839E4/0xE839E8
```

— that is, **"crop the screen to 16:9"**. On a 4:3 display that's 25% of the height
(12.5% per bar, e.g. 800×600 → a 800×450 visible area). On a 16:9 display it is
exactly **zero**, so the bars, although faithfully animated and drawn, have no
height. On 16:10 you get slivers (6.25% total).

The formula appears in five places, all the identical 12-byte instruction pair
`fild [0xE839E4]` / `fmul [0x8C7A50]`:

| vaddr | role |
|-------|------|
| `0x005C5786` | `HelpSystem` bar-height helper (`0x5C5780`, × fraction ÷ 2) — feeds the dialogue/help-text rect (`0x5C57B0`) during cutscenes |
| `0x0081E8B6` | shared bar-height helper (`0x81E8B0`, × fraction ÷ 2) — feeds the two black-bar drawers (`0x82F686`, `0x870154`) and the visible-area rect helpers (`0x81E881`, `0x81E8E1`, `0x81E922`) |
| `0x00456F22` | inline usable-height clamp in `GInterface` (mouse / UI placement), gated on the widescreen flag |
| `0x0045B978` | ditto |
| `0x0045D05F` | ditto |

## Fix

Replace each pair with a `call` into a 51-byte cave (`0x008A8C50`, in the `.text`
tail zero-pad after the [`widescreen_logos`](widescreen_logos.md) caves) that
computes

```
min(w, h * 4/3) * 0.5625
```

instead of `w * 0.5625` — the same effective-4:3-width trick as the other
widescreen patches. The cave preserves all integer registers and leaves the FPU
exactly as the replaced pair did (`st0` = product, `st1` = h), so all five call
sites work unchanged.

On 4:3 / 5:4 displays `min()` returns `w` and behaviour is bit-for-bit identical.
On wider displays the bars become the same fraction of the height they always were
on 4:3 — 12.5% per side — giving a ~2.37:1 visible area on 16:9, which happens to
be the classic cinema scope ratio (and what most modern games letterbox cutscenes
to). On ultrawide the bars keep that same fraction rather than tapering off.

Because bar drawing, text placement and the cutscene mouse/UI clamps all flow
through these five sites, everything stays in agreement: the help text sits above
the bottom bar, and the cursor is confined to the visible area exactly as on 4:3.

## How other games handle this (for context)

The original effect was authored as "make 4:3 look like cinema widescreen", which
is why it nulls out once the display is already 16:9. Modern games instead
letterbox cutscenes to a ratio *wider than any common display* (≈2.35–2.39:1) or
use a fixed bar fraction — both of which this patch effectively reproduces — or
drop bars entirely in favour of HUD removal and camera cues.

## Out of scope

* The movie player (`0x0054DBEB`) has its own copy of the formula for sizing the
  Bink destination rect between its bars; it is intentionally untouched here.
* The other user of the 0.5625 constant (`0x0044FB34`) is unrelated
  squared-distance math that merely shares the `.rdata` float; also untouched.

Bytes are generated by
[`scripts/widescreen_cinema_bars_asm.py`](../scripts/widescreen_cinema_bars_asm.py)
(keystone). Each hook op's `expect` is the original 12-byte pair, so the patch
refuses to apply to anything but a matching executable.
